摘要

本项目面向个人学习与日常事务管理，设计一款离线可用的 Android 任务清单应用。应用支持任务新增、编辑、完成、删除、关键词搜索、按状态筛选、截止日期提醒和数据备份。项目采用 Kotlin、Jetpack Compose、ViewModel、Room 与 WorkManager，按照界面层、领域层和数据层组织代码。任务数据保存在本地 SQLite 数据库中，界面通过 StateFlow 订阅状态变化，耗时操作在协程中执行。

项目重点处理任务状态一致性、日期边界、进程重启后的提醒恢复以及列表数据量增加后的响应速度。测试使用 500 条任务记录，覆盖新增、更新、筛选、重复提醒、过期任务和备份恢复等场景。12 项核心功能用例全部通过，冷启动后首屏显示时间为 430 ms，500 条记录关键词筛选耗时为 18 ms，应用在无网络状态下能够正常完成全部基础操作。

关键词

Android；Kotlin；Jetpack Compose；Room；WorkManager；任务管理

设计目标

1. 项目背景

学习任务通常同时存在课程、截止时间、优先级和完成状态。仅使用便签记录时，任务容易被旧内容淹没，也难以快速查看“今天到期”或“尚未完成”的项目。现有在线工具功能较多，但课程项目需要在不依赖服务器的条件下完成完整的数据录入、状态管理、筛选和提醒流程，因此选择个人任务清单作为设计课题。

2. 功能目标

应用应支持创建任务，字段包括标题、备注、分类、优先级、截止时间和是否提醒；支持修改与删除任务；支持一键切换完成状态；支持按全部、未完成、今天、已过期和已完成筛选；支持按标题与备注关键词搜索；支持把数据导出为 JSON 文件并从备份恢复。

3. 质量目标

所有写操作必须经过输入校验，空标题不得保存；截止时间按本地时区统一转换为时间戳；提醒任务在设备重启或应用进程被回收后仍能重新调度；列表状态由单一数据源提供，界面不得维护与数据库相互独立的任务副本。500 条数据下筛选操作应在 100 ms 内完成，普通增删改操作应在 300 ms 内反馈结果。

开发环境

开发系统为 Windows 11，Android Studio 2025.1，JDK 17，Kotlin 2.0。界面使用 Jetpack Compose Material 3，最低系统版本为 Android 8.0，目标版本为 Android 15。数据库使用 Room 2.6，异步处理使用 Kotlin Coroutines 1.8，后台提醒使用 WorkManager 2.9，单元测试使用 JUnit 5，界面测试使用 AndroidX Test。

测试设备包括 Android 15 模拟器和一台 Android 12 测试设备。项目使用 Gradle Kotlin DSL 管理依赖，调试数据库通过 Android Studio App Inspection 查看。备份文件使用 UTF-8 编码的 JSON 格式，测试期间不接入账号、云服务或第三方统计组件。

需求分析

1. 用户与使用场景

系统只有本机用户，不设置登录流程。典型操作包括：课后录入作业和截止日期；在首页查看今天需要处理的事项；完成任务后勾选状态；通过课程分类和关键词查找历史任务；更换设备前导出备份。应用必须在无网络环境下可用。

2. 数据需求

任务实体 TaskEntity 包含 id、title、note、category、priority、dueAt、remindAt、completed、createdAt 和 updatedAt。id 使用自增主键，title 不允许为空，priority 取 LOW、NORMAL、HIGH 三个值。remindAt 可以为空，但存在时不得晚于 dueAt。分类以普通字符串保存，去除首尾空格后参与筛选。

3. 状态与筛选需求

首页需要显示未完成数量、今日到期数量和已过期数量。筛选条件与搜索词可以同时生效，例如在“未完成”范围内搜索“数据库”。完成任务后应取消尚未触发的提醒；从已完成恢复为未完成时，如果提醒时间仍在未来则重新调度。删除任务要同时删除数据库记录和对应后台工作。

4. 异常与安全需求

备份导入前必须检查版本号和字段完整性，解析失败时不得覆盖现有数据库。恢复过程先写入事务，全部记录校验通过后再提交。文件选择通过系统 Storage Access Framework 完成，不申请整个存储空间权限。通知权限只在用户首次启用提醒时请求。

方案设计与实现

1. 总体结构

项目分为 presentation、domain 和 data 三层。presentation 包含 Compose 页面、导航、ViewModel 和 UI State；domain 包含 Task、TaskFilter、校验规则及用例；data 包含 Room Entity、DAO、Repository、备份序列化和提醒调度器。ViewModel 只调用用例，不直接持有 DAO。Repository 负责实体与领域对象转换，并把数据库 Flow 暴露给上层。

2. 数据表与索引

task 表以 id 为主键，title、completed、due_at 和 updated_at 建立索引。TaskDao 提供 observeTasks、insert、update、deleteById 和 replaceAllInTransaction。列表查询不为每种筛选写一条固定 SQL，而是先由 Room 返回满足状态和日期范围的结果，再在领域层组合少量关键词过滤；当数据规模超过课程项目范围时，可把全文检索迁移到 FTS 表。

3. 页面与交互

首页顶部显示三个统计卡片，中部为筛选标签和搜索框，下部为 LazyColumn 任务列表。任务卡片展示标题、分类、截止时间和优先级，过期任务使用文字和图标共同提示，不只依赖颜色。右下角浮动按钮打开任务编辑页。编辑页按“基本信息、时间、提醒”分组，保存按钮仅在标题有效且时间关系正确时可用。

4. 状态管理

TaskListViewModel 将 DAO 的任务流、搜索词和筛选条件通过 combine 合并为 TaskListUiState。界面只收集一个状态对象，避免任务列表、数量卡片和空状态分别订阅后产生短暂不一致。新增和编辑使用 SavedStateHandle 保存草稿，旋转屏幕或进程恢复后可以继续填写。

5. 提醒设计

每个提醒任务使用唯一名称 task-reminder-{id} 调度 OneTimeWorkRequest。保存任务时先提交数据库，再根据 remindAt 创建或替换后台工作；完成或删除任务时按唯一名称取消。ReminderWorker 执行前再次读取数据库，只有任务仍存在、未完成且提醒时间有效时才发出通知，从而避免旧工作产生重复提醒。

6. 备份与恢复

备份文件包含 schemaVersion、exportedAt 和 tasks 数组。导出时先读取一致性快照，再写入临时文件，完成后交给系统文档提供器。恢复时解析到内存，逐条检查标题、枚举值和日期关系；确认无误后在单一事务中替换数据。恢复完成后重新扫描未来提醒并调度 WorkManager。

7. 关键处理

“今天”以设备本地时区的 00:00 至下一日 00:00 作为半开区间，避免 23:59:59 精度问题。逾期定义为 dueAt 小于当前时间且 completed 为 false。搜索时统一转为小写并去除首尾空格，标题和备注任一包含关键词即匹配。任务排序先按完成状态，再按是否逾期、优先级、截止时间和创建时间。

实现结果

1. 基础功能

应用能够新增、编辑、完成和删除任务。空标题会在输入框下方显示提示且保存按钮不可用。新建“数据库实验报告”，截止时间设为当天 22:00，保存后立即出现在“今天”列表；勾选完成后统计卡片数量同步减少，重新打开应用后状态保持。

2. 筛选与搜索

测试库包含 500 条任务，其中未完成 286 条、今天到期 18 条、已过期 23 条。输入关键词“网络”并选择“未完成”，列表返回 16 条记录，结果均满足两个条件。筛选切换没有出现重复项或旧统计值。500 条记录的关键词筛选中位耗时为 18 ms。

3. 提醒与恢复

创建 2 分钟后提醒的任务，退出应用后通知按时出现。编辑提醒时间后旧工作被替换，只收到一次通知。完成任务后通知取消。模拟应用进程终止并重启，未来提醒仍存在。导出 500 条记录后清空数据库，再从备份恢复，任务数量、完成状态和提醒数量与导出前一致。

4. 用例执行情况

核心测试包括空标题、非法时间关系、任务新增、完成状态切换、组合筛选、过期边界、唯一提醒替换、完成后取消、删除后取消、备份导出、损坏备份拒绝和完整恢复，共 12 项，全部通过。Android 15 模拟器冷启动到首屏数据可见的时间为 430 ms，新增任务保存反馈为 74 ms。

问题与改进

初版在列表页面分别收集任务、未完成数量和今日数量三个 Flow，快速完成任务时三个区域更新顺序不同，出现短暂数字不一致。改为在 ViewModel 中合并为单一 UiState 后解决。第二个问题是提醒工作名称使用任务标题，标题修改后旧工作无法找到；改为稳定的任务 id 后可以准确替换和取消。

当前项目仍有三点可改进。第一，关键词筛选在内存完成，数据超过数万条时应使用 Room FTS。第二，备份只支持全量替换，后续可增加冲突预览和按更新时间合并。第三，提醒时间依赖系统调度，省电策略下可能存在少量延迟；若业务要求精确到分钟，需要评估精确闹钟权限及其使用边界。

设计总结

本项目完成了离线任务管理、组合筛选、状态统计、提醒和备份恢复的完整流程。实现过程中最重要的设计决定是保持单一数据源：数据库负责持久状态，ViewModel 负责组合界面状态，WorkManager 在执行前再次核对数据库。这样可以避免界面、数据和后台任务各自保存一份状态。

课程项目也说明，功能可用之外还需要处理边界条件和恢复路径。日期应使用明确区间，后台工作需要稳定标识，导入数据必须先校验后提交。通过测试这些容易被忽略的路径，应用在进程重启、无网络和异常备份等情况下仍能保持可预测行为。
